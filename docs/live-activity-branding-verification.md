# Live Activity branding investigation and verification

## Findings

- `WorkoutLiveActivityWidget.swift` is also the `@main` widget bundle entry point and registers `WorkoutLiveActivityWidget`. On main, the Lock Screen header renders only `Text("WakTrainer")`; commit `089b42e` removed its logo after an earlier image-based fix. Compact, minimal, and expanded leading regions render generic workout SF Symbols. The missing custom brand is therefore explicit in the view code; it is not evidence that iOS cannot locate the containing app icon.
- All three apps (production, Demo, DeviceTest), in Debug and Release, use `ASSETCATALOG_COMPILER_APPICON_NAME = AppIcon`, include the synchronized `WakTrainer` group, and enable `NSSupportsLiveActivities`. `AppIcon.appiconset` contains its declared 1024px source. There is no missing filename or separate Demo app icon catalog to repair.
- All three widget targets include the synchronized `WakTrainerWorkoutWidget` group with no exclusions, including its asset catalog. Each app depends on and embeds its corresponding widget. The shared extension plist declares `com.apple.widgetkit-extension` correctly. An empty explicit resources list is expected with these filesystem-synchronized groups.
- The old `WakTrainerAppLogo.imageset` contains a **1024 × 1024 image with no scale**, byte-identical to the existing app icon. That is a 1024pt source, despite the previous SwiftUI frame being 22pt. Apple constrains the source image resolution used by ActivityKit, so restoring the previous Image/frame alone retains an invalid source-size risk. The historical device failure cannot be conclusively attributed to this without its runtime logs.

## Fix

Use the existing widget logo, regenerated by deterministic downsampling of the byte-identical original app icon into a 24pt imageset at 1x, 2x, and 3x (24/48/72 pixels). No new mark, recoloring, crop, or added container. Keep original rendering intent in the catalog and SwiftUI so the green logo remains visible on the existing dark Lock Screen surface and Dynamic Island's black surface regardless of the system appearance. The original image's baked-in background is preserved.

Resolve the image explicitly in `Bundle.main`, which in this source is the extension bundle. Restore a 22pt logo beside the existing Lock Screen app name; use a 20pt logo in the existing expanded leading label, compact leading slot, and minimal slot. Timer, workout name, heart rate, zone, calories, sets/distance, and existing interactions remain intact. No controller, HealthKit, session, or update scheduling changes.

## Apple presentation rules

- [Displaying live data with Live Activities](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities): developers provide Lock Screen and Dynamic Island presentations in a widget extension. Images must not exceed the presentation's dimensions; Apple's minimal example limit is 45 × 36.67pt. SwiftUI resizing alone does not change the source asset dimensions. Live Activities cannot download their images over the network.
- [Live Activities HIG](https://developer.apple.com/design/human-interface-guidelines/live-activities): the system chooses compact/minimal/expanded presentations, and Dynamic Island has an opaque black background. Branding inside those presentations is developer content; there is no promise that iOS inserts a notification-style app icon there. System-owned app identity/icons in other contexts remain controlled by the containing app's AppIcon. The HIG recommends an uncontained logo mark, rather than an entire app icon; this fix reuses the repository's existing logo artwork without introducing a replacement design or another container.

## Automated verification

Run `python3 scripts/validate-live-activity-branding.py` on macOS. This checks all three app/widget pairs, both configurations, synchronized asset membership, embedding/dependencies, AppIcon filenames, Live Activities and extension settings, original rendering intent, and the PNG source dimensions/scales. CI runs this before building.

`LiveActivityBrandingTests` loads the compiled logo from the **embedded extension bundle** on a simulator, across light/dark traits and 1x/2x/3x scales. It asserts the actual loaded size and original rendering mode. This verifies compiled bundle resolution, not on-screen ActivityKit rendering.

## Runtime verification checklist (required before visual sign-off)

Use the existing Demo app's Live Activity Test screen (Start Test / End Test), plus a real production workout on a physical Dynamic Island iPhone. Do not treat ActivityKit accepting a request as proof of rendering.

- Capture Lock Screen, compact, expanded (long press), and minimal (another simultaneous Live Activity) on a supported iPhone.
- Repeat with system Light and Dark appearances; check the original green mark against each surface.
- Check running and paused states, long workout names, and both strength/cardio. Confirm timers, heart rate/zone, calories, sets/distance remain legible.
- Confirm a tap still opens the corresponding workout route and that the system-owned app identity uses the existing app icon wherever iOS displays it.
- Repeat production and Demo; DeviceTest shares the same widget source/catalog but must embed its own extension.

A build, asset inspection, or bundle-loading test does **not** constitute visual confirmation. No physical-device screenshots have been supplied for this fix.
